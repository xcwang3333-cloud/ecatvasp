# ADR-081: v1.0 Desktop Scientific Workspace Views

- Status: Accepted
- Date: 2026-09-07

## Context

v1.0 Blocks 1 through 4 established a strict stateless desktop IPC boundary, the local Python sidecar,
a Tauri + Svelte/TypeScript shell, and safe desktop-local project lifecycle preferences. v0.9 already
provides the authoritative read/presentation contracts needed by a research workspace:

- `WorkspaceProjection` with separate Calculation, Analysis, ExecutionAttempt, and scheduler-status
  namespaces;
- `WorkspaceScientificInventory` with provenance, dependencies, current scientific hashes,
  authoritative freshness, and attention codes;
- optional `WorkflowReadinessDashboard` projections;
- `ecatvasp-scientific-presentation-v1` datasets for structure, DOS/PDOS, COHP/ICOHP, and reaction
  diagrams;
- `ecatvasp-matterviz-v1`, locked to MatterViz 0.6.0, with an exact atom-index map and display policy;
- `ecatvasp-frontend-handoff-v1`, which combines those contracts through the reporting validation
  boundary.

Block 5 must turn those existing contracts into an actual scientific workspace without moving
scientific authority into TypeScript, Rust, MatterViz, browser state, filenames, plotting style, or
frontend caches.

## Decision

### 1. The desktop consumes the existing report/handoff contract, not a second workspace schema

The frontend parses the existing `ecatvasp-scientific-report-v1` payload inside
`ecatvasp-frontend-handoff-v1`. The TypeScript model is a strict transport representation of the
Python payload. It does not calculate scientific values, infer missing relations, or persist a second
scientific model.

The handoff and report hashes remain non-scientific cache/currentness identifiers only.

### 2. Lifecycle/status namespaces remain visibly separate

The workspace renders Calculation, Analysis, ExecutionAttempt, and scheduler-job status as four
separate domains. No UI reducer may reinterpret:

- scheduler success as Calculation convergence;
- ExecutionAttempt completion as scientific success;
- Analysis completion as Calculation convergence;
- workflow readiness as scheduler state.

This separation is visible in the overview and workflow-readiness surfaces.

### 3. Freshness, blockers, provenance, and dependencies are first-class views

Inventory rows expose the backend-provided:

- entity id and kind;
- status domain and status;
- current scientific hash;
- freshness state and exact reason codes;
- attention codes;
- provenance records;
- incoming/outgoing scientific or execution dependency records;
- scientific ancestor ids.

The desktop does not suppress stale, invalid, superseded, or blocked rows merely to simplify the UX.
Dependency kind and recorded source hash remain inspectable.

### 4. Desktop structure presentations are rebuilt from the current ProjectStore on every handoff

For desktop `frontend_handoff` requests, the Python adapter reopens the current `ProjectStore` and
builds one `StructurePresentationDataset` for every current `StructureSnapshot` through the existing
`build_structure_presentation()` authority. The resulting handoff still passes through
`build_frontend_handoff()` / `build_scientific_report()` validation.

This is a read/presentation enrichment only:

- no StructureSnapshot is created or changed;
- no presentation is persisted;
- no provenance/dependency record is added;
- no scientific hash is generated by the frontend;
- no cached structure presentation survives a later project reopen as authority.

DOS/PDOS, COHP/ICOHP, and reaction-diagram presentations remain caller-supplied authoritative DTOs;
the desktop does not guess which stored result, selector set, or CHE conditions should be presented.

### 5. Workflow readiness is displayed only when an authoritative dashboard is supplied

`WorkflowReadinessDashboard` requires current scientific gate evidence and may depend on explicit
accepted-structure source information that is intentionally not reconstructed from filenames,
history order, or proximity. Therefore Block 5 does not synthesize readiness in TypeScript or invent a
new Python fallback.

When `workflow_readiness` is present in the handoff, the desktop displays its exact:

- scientific state;
- readiness verdict;
- gate reason codes;
- current generation and Calculation id/status;
- superseded binding/Calculation ids;
- ExecutionAttempt history;
- RemoteJob scheduler observations;
- orchestration action/reasons;
- edge verdicts and accepted StructureSnapshot ids.

When it is absent, the UI says that no authoritative readiness dashboard was supplied. It does not
replace that absence with a heuristic verdict.

### 6. Structure rendering preserves the frozen atom-index frame

MatterViz 0.6.0 is now an actual desktop dependency, still desktop-only. The viewer receives the
backend-produced `matterviz.structure` object directly.

The frontend transport guard verifies that:

- `ecatvasp-matterviz-v1` and target version 0.6.0 are exact;
- the number of sites equals `atom_uid_by_viewer_index` length;
- `viewer_index_by_atom_uid` is an exact inverse mapping;
- each site `ecatvasp_atom_uid` equals the uid assigned to that exact viewer index;
- overlay indices are in range;
- the display policy remains `original`, `1x1x1`, no supercell scaling, and no image atoms.

Only explicit backend overlay binding segments become MatterViz `StructureBond` records. The desktop
never performs nearest-neighbor bonding or filename-based atom/species inference.

### 7. Old structure presentations fail closed against the same handoff inventory

For every structure presentation, the TypeScript transport guard requires:

`presentation.source_scientific_hash == inventory[current StructureSnapshot].current_scientific_hash`.

A missing snapshot row, missing current hash, or mismatched source hash is a contract/currentness
failure. The UI must refresh from Python rather than display the old presentation as current.

This check does not replace Python reporting validation; it is a downstream consistency guard across
two fields already supplied by the same validated handoff.

### 8. Other scientific presentation semantics are displayed without plot reinterpretation

Block 5 renders presentation metadata and canonical data semantics conservatively:

- DOS/PDOS keeps the backend energy reference, Fermi energy, units, selectors, and native values; no
  smoothing, clipping, aggregation, or spin inversion is introduced;
- COHP/ICOHP explicitly remains `lobster_native`; the desktop does not silently transform to -COHP;
- reaction diagrams preserve the requested CHE conditions, ordered states/steps, units, and source
  hashes.

Plot styling, visibility, axis ranges, selection, camera, and panel layout remain non-scientific local
UI state under ADR-077.

### 9. Refresh is path-scoped and stateless

Opening, switching, restoring, or manually refreshing a project requests a fresh handoff using the
explicit project path. The browser does not retain an authoritative ProjectBundle or session handle.
If refresh fails, the selected project may remain selected, but the workspace is shown as unavailable
rather than silently serving a different project's data.

### 10. Persistence, schema, and scientific identity remain frozen

Block 5 adds no permanent entity or migration:

- `SCHEMA_VERSION` remains 3;
- package version remains `1.0.0.dev0`;
- ProjectStore schema is unchanged;
- scientific hashes and `DependencyKind.SCIENTIFIC` remain Python authorities;
- frontend report/handoff/view state is non-scientific and non-provenance.

## Desktop surfaces

The Block 5 workspace contains:

1. a project/scientific overview with exact entity counts and four separate lifecycle domains;
2. freshness and attention summary;
3. searchable/inspectable scientific inventory rows;
4. provenance inspection;
5. dependency inspection;
6. workflow readiness dashboards when authoritative projections are supplied;
7. structure presentations through MatterViz with visible snapshot/source identity and atom-index
   mapping;
8. conservative metadata/data views for DOS/PDOS, COHP/ICOHP, and reaction diagrams when supplied.

## Acceptance contract

Block 5 is accepted only if tests and CI prove that:

1. the frontend rejects incompatible report/presentation/MatterViz contract versions;
2. Calculation, Analysis, ExecutionAttempt, and scheduler status remain separate;
3. stale/blocked/attention reason codes remain visible in the parsed view model;
4. provenance ids, tool/version, parameters hash, MethodFingerprint id, and dependency kind/hash remain
   inspectable without recomputation;
5. a structure handoff contains exact current snapshot id, current source scientific hash, and exact
   atom-index mapping;
6. a later persisted change that keeps the snapshot UUID but changes its scientific content produces a
   new desktop structure presentation/source hash after refresh;
7. a structure presentation whose source hash disagrees with the same handoff inventory is rejected;
8. MatterViz receives only the exact frozen index frame and explicit binding segments; no proximity or
   filename inference exists;
9. absence of authoritative workflow readiness is shown as absence, not guessed;
10. DOS/PDOS, COHP/ICOHP, and reaction metadata preserve energy reference, units, sign convention, and
    requested conditions when supplied;
11. open/switch/refresh never persists workspace state into ProjectStore;
12. Ruff, strict mypy, pytest on Python 3.11/3.12/3.13, MatterViz contract, desktop Svelte typecheck,
    Vitest, Vite build, Rust tests, and `cargo check` remain green.

## Non-scope

Block 5 does not add:

- typed scientific mutations or scheduler submission controls (Block 6);
- automatic reconstruction of workflow gate evidence;
- automatic selection of DOS/COHP/reaction analyses or CHE conditions;
- new scientific plot transformations;
- durable Study/sweep/ranking entities;
- schema v4;
- Windows packaging (Block 7);
- resilience/export hardening (Block 8);
- tag, GitHub Release, or PyPI publication.

## Consequences

ECatVASP now has a production desktop read surface that is rich enough for scientific inspection while
remaining downstream of the Python authorities. Structure viewing becomes immediately interactive,
but the UI still cannot manufacture scientific currentness, readiness, convergence, identity, or
provenance.
