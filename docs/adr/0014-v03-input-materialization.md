# ADR-014: v0.3 Immutable VASP Input Materialization and Manifest

- Status: Accepted
- Date: 2026-09-03

## Context

Blocks 2–5 produce deterministic in-memory VASP preparations for POSCAR, atom identity,
POTCAR metadata, k-points, and INCAR. Block 6 must cross the filesystem boundary without
weakening the frozen scientific model:

- generated inputs must remain attributable to one immutable `Calculation`;
- `atom_uid` identity must survive the POSCAR serialization boundary;
- redistribution-safe `POTCAR.spec` may be persisted, but licensed POTCAR bodies must not be;
- generated bytes must be immutable once materialized for a Calculation;
- an execution attempt must later be able to pin one exact input set with
  `ExecutionAttempt.input_manifest_hash`;
- persisted files must participate in existing Artifact / provenance / freshness semantics;
- schema version 1 must remain unchanged.

Established open-source VASP tooling such as pymatgen/atomate2 also separates input-set
construction from writing to a directory and supports writing `POTCAR.spec` instead of licensed
POTCAR content. ECatVASP adopts that safe file boundary while retaining its own domain,
fingerprint, atom-identity, and provenance contracts.

## Decision

### Calculation-owned immutable input directory

One materialized input set is written beneath:

`calculations/<calculation_id>/inputs/`

The materializer may create or re-read byte-identical files, but it never replaces an existing
path with different bytes. A conflicting existing file fails closed.

Block 6 materializes only redistribution-safe inputs:

- `POSCAR`
- `INCAR`
- `KPOINTS` when the Block 4 plan uses a KPOINTS file
- `POTCAR.spec`
- `atom-index-map.json`
- `input-manifest.json`

For KSPACING policies, no `KPOINTS` file is created. A licensed combined `POTCAR` is never written
by this block.

### Existing Artifact schema

No new frozen Artifact type is introduced.

- POSCAR -> `ArtifactType.POSCAR`
- INCAR -> `ArtifactType.INCAR`
- KPOINTS -> `ArtifactType.KPOINTS`
- POTCAR.spec -> `ArtifactType.POTCAR_SPEC`
- atom-index-map.json -> `ArtifactType.DERIVED_DATASET`
- input-manifest.json -> `ArtifactType.DERIVED_DATASET`

All generated inputs are Calculation-produced, LOCAL, and `RetrievalPolicy.ALWAYS`. Artifact
metadata records project-relative path, byte size, and exact SHA-256.

### Atom index sidecar

`atom-index-map.json` records the exact snapshot id/hash, POSCAR hash, species order/counts, and
for every serialized atom:

- permanent `atom_uid`
- element
- immutable-snapshot index
- zero-based POSCAR-local index
- one-based VASP ordinal
- resolved Selective Dynamics flags when present

VASP ordinals therefore remain serialization-local metadata rather than scientific atom identity.

### Deterministic input manifest

The manifest is deterministic and does not include random Artifact UUIDs or its own hash. It
contains:

- Calculation id/type/engine and scientific hash
- StructureSnapshot id and scientific hash
- MethodFingerprint id plus core/protocol/instance hashes
- Recipe id/version/hash
- input-materializer contract name/version
- physical VASP system context
- exact preparation hashes
- effective INCAR parameters with Method/Protocol/Recipe/Context source layers
- resolved k-point representation
- redistribution-safe POTCAR metadata and POTCAR metadata hash
- project numerical-lock hash when present
- project-relative generated-file paths, sizes, Artifact types, and content hashes
- one deterministic `preparation_hash` over the complete preparation contract

`input-manifest.json` is itself content hashed. Its SHA-256 is the value that a later
`ExecutionAttempt.input_manifest_hash` will pin.

### Provenance and freshness

Every materialized Artifact receives a `ProvenanceRecord` identifying the Block 6 materializer,
its contract version, the MethodFingerprint, and the preparation hash.

Scientific dependencies record the exact hashes of the immutable upstream snapshot,
MethodFingerprint, and Calculation intent for each generated input Artifact. The manifest
Artifact additionally depends on every file Artifact using the file content SHA-256. Existing
freshness propagation can therefore detect scientific upstream changes without introducing a
second dependency graph.

### Validation boundary

Materialization fails closed when any supplied prepared object diverges from the immutable
Calculation / MethodFingerprint contract, including snapshot id, recipe id, MethodFingerprint id,
system context, POTCAR species/core-method identity, Protocol ENCUT, k-point policy, or project
numerical lock.

Block 6 does not create or submit an `ExecutionAttempt`, stage licensed POTCAR contents, create
scheduler scripts, connect to SSH, or construct RemoteJob state. Those remain beyond this block.

## Consequences

- A generated VASP input directory becomes inspectable, reproducible, and byte-addressed.
- The manifest provides the stable handoff between scientific input generation and later
  execution attempts.
- Atom identity survives all VASP-local ordering decisions.
- POTCAR licensing boundaries remain explicit.
- Existing Artifact / provenance / freshness / storage schema is reused without schema drift.
- Block 7 can build end-to-end core recipes on a concrete immutable input-set contract.
